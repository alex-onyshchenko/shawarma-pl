# Шаурма на Вугіллі — незалежні застосунки та сервіс синхронізації

Репозиторій містить автономні підпроєкти. Кожен має власні залежності,
lock-файл, конфігурацію та Dockerfile. Каталог будь-якого підпроєкту можна
скопіювати в окремий репозиторій і встановити через `npm ci`.
Немає npm workspaces, спільних runtime-пакетів або імпортів із сусідніх проєктів.

| Підпроєкт | Каталог | Локальний порт | Призначення |
| --- | --- | --- | --- |
| Client | `apps/client` | 3000 | Telegram Mini App, меню, кошик, статус замовлення |
| Kitchen | `apps/kitchen` | 3001 | Термінал кухаря KDS |
| Sync | `services/sync` | 3002 | REST API, SSE, поточне сховище замовлень |
| Analytics | `apps/analytics` | 3003 | Окрема опційна панель аналітики |

Client і Kitchen взаємодіють через Sync за HTTP/SSE. Вони не потребують
доступу до коду або сервера іншого фронтенду. Наявні локальні браузерні
fallback-події не замінюють Sync між різними портами, доменами чи пристроями.

## Локальний запуск

Потрібен Node.js 24 та npm. Docker для цього способу не потрібен.

Встановити залежності всіх підпроєктів із кореня:

```bash
npm run setup
```

В окремих терміналах:

```bash
npm run server
npm run dev:client
npm run dev:kitchen
# Опційно:
npm run dev:analytics
```

Відкрити `http://localhost:3000`, `http://localhost:3001` та,
за потреби, `http://localhost:3003`. Кожен інтерфейс має власний `index.html`
і відкривається за `/`. Попередні команди `npm run dev` та `npm run dev:kds`
залишені як аліаси.

Кореневий package.json — лише набір зручних команд; встановлювати залежності
в корені не потрібно. Для роботи тільки з одним підпроєктом:

```bash
cd apps/client
npm ci
npm run dev
npm run build
npm run preview
```

Для Kitchen та Analytics команди аналогічні. Для Sync:

```bash
cd services/sync
npm ci
npm start
# Автоматичний перезапуск під час розробки:
npm run dev
```

## Налаштування адрес

Кожен підпроєкт має `.env.example`. Скопіюйте його в `.env`, якщо потрібно
змінити значення за замовчуванням.

Фронтенди:

- `SYNC_API_TARGET` — адреса Sync для Vite dev/preview proxy; за замовчуванням
  `http://127.0.0.1:3002`. Не потрапляє до браузерної збірки.
- `VITE_SYNC_API_URL` — публічний URL API, наприклад `https://api.example.com`.
  Без `/api` в кінці. Порожнє значення використовує `/api` на домені фронтенду.
  Однакова конфігурація застосовується до REST і SSE.
- `VITE_KITCHEN_URL` у Client та `VITE_CLIENT_URL` у Kitchen — адреси
  допоміжних посилань між інтерфейсами; локальні значення є у `.env.example`.

Значення `VITE_*` вбудовуються під час `npm run build`, тож після їх зміни
потрібна нова збірка. `SYNC_API_TARGET` діє тільки у Vite dev/preview;
для статичного хостингу налаштуйте reverse proxy `/api` або публічний
`VITE_SYNC_API_URL`. HTTPS-фронтенд повинен звертатися до API через HTTPS.

Sync читає `HOST` (типово `0.0.0.0`) і `PORT` (типово `3002`) з оточення
або локального `.env` під час `npm start` / `npm run dev`.

## Docker Compose

```bash
docker compose up --build
# Із панеллю аналітики:
docker compose --profile analytics up --build
```

Порти ті самі, що й локально. Кожен frontend image збирається тільки зі
свого каталогу та віддає статичну збірку через nginx. `/api` проксіюється
до `sync:3002`, тому браузеру не потрібні внутрішні Docker-адреси.
SSE-проксіювання працює без буферизації. Compose очікує healthcheck Sync.

Кожен image можна збирати окремо, наприклад:

```bash
docker build -t shawarma-client apps/client
docker build -t shawarma-kitchen apps/kitchen
docker build -t shawarma-sync services/sync
```

Для автономного розгортання frontend-контейнера підмонтуйте власний
`nginx.conf` у `/etc/nginx/conf.d/default.conf` з доступною адресою Sync.
Наданий конфіг очікує DNS-ім'я `sync` у контейнерній мережі Compose.

## Перевірки

```bash
npm run build   # Усі три фронтенди, кожен у власний dist/
npm run check   # Синтаксис сервера
npm test        # Автономний сервіс: health, REST, SSE, статуси й архів
npm run test:integration # REST/SSE між окремими Vite-проксі та Sync
```

Інтеграційний тест запускає окремий сервер на вільному локальному порту,
не змінює даних робочого процесу та завершує тестовий сервер після перевірки.

Контракт HTTP/SSE описаний у `services/sync/API.md`. Транспортні адаптери
Client і Kitchen зберігаються локально в кожному застосунку: зміни API слід
узгоджувати між ними через контракт, без імпортів через межі проєктів.

## Поточні обмеження

Цей поділ змінює структуру та спосіб запуску, але зберігає демонстраційну
бізнес-логіку: Sync тримає дані в пам'яті та генерує тестову історію,
авторизації й реальної платіжної інтеграції поки немає. Перезапуск Sync
втрачає поточні замовлення. Для реальних замовлень потрібні окремі роботи
над збереженням даних, перевіркою запитів та оплатою.
