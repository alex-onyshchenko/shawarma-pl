# Sync API — MVP часу видачі

REST і SSE доступні через `/api` на домені кожного фронтенду або напряму
на порту 3002. Час зберігається як Unix timestamp у мілісекундах.
За замовчуванням часовий пояс закладу — `Europe/Kyiv`, робота 10:00–22:00.
Часовий пояс і графік беруться з бази точки та редагуються через Admin із точністю до хвилин.
Змінні оточення не визначають розклад. Початкові значення записуються лише в порожню базу.
Нічні зміни не підтримуються.

## Доступність

`GET /api/availability` повертає:

```json
{
  "timeZone": "Europe/Kyiv",
  "openMinute": 600,
  "closeMinute": 1320,
  "serverNow": 1792661400000,
  "slots": [],
  "acceptingOrders": true,
  "asapAvailable": true
}
```

`slots` — лише сьогодні, у межах роботи, з кроком 15 хвилин. Перший слот:
округлення `serverNow + 15 хв` угору до чверті години. `acceptingOrders` —
ручний перемикач адміністратора; відсутність слотів також обмежує оформлення.
ASAP доступний з відкриття, якщо до закриття лишається мінімум 15 хвилин.

`acceptingOrders` — ручний статус кафе: true = «Відчинено», false =
«Зачинено». Кухар перемикає його у своєму терміналі; розклад самостійно
не змінює цей статус. Клієнт отримує його через `availability_updated` та
знімки `/api/orders` і показує під адресою.

`PATCH /api/settings` працює без адміністративного пароля для термінала
кухаря. `{ "acceptingOrders": true/false }` відчиняє або зачиняє кафе;
ця дія також скидає перерву. `{ "onBreak": true/false }` починає або завершує
обідню перерву у відчиненому кафе. Перерва у зачиненому кафе — 409.
Статус зберігається в SQLite та передається через `availability_updated`.
В availability: `cafeOpen` — кафе відчинене, `onBreak` — обідня перерва,
`acceptingOrders = cafeOpen && !onBreak` — можна оформляти нові замовлення.
Клієнт показує «Обідня перерва», закриває оформлення; вже створені замовлення
можна виконувати та відновлювати повторним запитом. Авторизація `/api/admin`
залишається без змін.

## Оформлення та оплата при отриманні

`POST /api/orders` приймає `items`, `totalPrice`, контактні дані,
`orderType`, `paymentMethod`, `timingMode` (`asap` / `scheduled`) та
`requestedReadyAt` (число, для scheduled). `clientRequestId` — ключ повторної
спроби: повторний запит повертає вже створене замовлення, навіть під час стопу.
Для нового замовлення відповідь 201, для відновлення повторного — 200.

Час ASAP — поточний серверний час +15 хв, округлений вгору до
найближчої чверті години (16:53 → 17:15). Для scheduled сервер
перевіряє кратність 15 хв і сьогоднішні години роботи. Застарілий вибір
автоматично переноситься до найближчого доступного слота. Якщо сьогодні
слотів уже немає, запит відхиляється до імітації оплати.

Додаткові поля відповіді:

- `baselineReadyAt`: базовий час, який кухня надалі не змінює;
- `requestedReadyAt`: початковий вибір;
- `timingAdjusted`: автоматичне перенесення застарілого часу;
- `confirmedReadyAt`, `acceptedAt`: null до підтвердження кухнею;
- `kitchenDelayMinutes`: 0, 5, 10 або 15;
- `paymentStatus`: `cash_due` для нових замовлень, `paidAt`: null;
- `paymentMethod`: `cash`; онлайн-методи відхиляються з 409;
- `napkins`: boolean; `cutlery`: false; `phoneNumber` може бути порожнім;
- `paymentSimulation`: true; реальних списань і зовнішніх викликів немає;
- `notification`: актуальний текст імітації Telegram-повідомлення;
- `timeZone`: пояс закладу.

У клієнтському MVP доступний лише самовивіз; кнопки доставки й картки
неактивні. Демо-точка: м. Полтава, вул. Соборності, 46, без знижки за
самовивіз. Кошик отримує адресу з `/api/menu`, сервер зберігає її зі своєї БД.
Довільні побажання, загальний коментар і промокод прибрані з клієнта.
`items[].toastingLevel` для шаурми — `light` («Слабіше»), `normal`
(«Звичайна піджарка», за замовчуванням) або `strong` («Сильніше»). Сервер перевіряє варіант і зберігає його разом із
підписом `toasting` у знімку позиції. Підсмаження не впливає на ціну.

`items[].sizeId` обов'язковий для товару з розмірами. `sizes` у меню містить
`id`, `name`, `weight`, `price`; сервер бере ціну обраного розміру зі свого
меню точки. Замовлення зберігає `sizeId`, `sizeName`, `weight` та назву з
розміром для кухні. Невідомий розмір дає 409. Зміна локальних розмірів у
адмінці: `PATCH /api/admin/points/:id/menu/:productId` з `{ sizes: [...] }`.
Ціна картки автоматично дорівнює мінімальній ціні розміру.

## Ручне замовлення з кухні

`POST /api/kitchen/orders` приймає ті самі `items`, `clientRequestId`,
`expectedTotal`, `requestedReadyAt`, що й клієнтський маршрут. Час — у найближчі 24 години, кратний 15 хв і щонайменше через 15 хв.
Застарілий слот переноситься вперед. Ручне замовлення можна створити
поза розкладом, у зачиненому кафе й під час перерви; статус кафе для клієнтів
при цьому не змінюється. `GET /api/availability` повертає `manualSlots`
незалежно від розкладу. Клієнтські замовлення зберігають усі перевірки
розкладу, закриття та перерви.
Відповідь 201 містить `source: kitchen`, `timingMode: scheduled`,
`acceptedAt` і `confirmedReadyAt`: час одразу підтверджено, статус — `new`.
Ціни й доступність перевіряє сервер. Створення й підтвердження атомарні;
повторний `clientRequestId` повертає існуюче замовлення з 200. Захист від
завчасного приготування зберігається. Права доступу такі самі, як в інших
операційних маршрутах KDS для прийняття та зміни статусу замовлення.

Фото трьох шаурм зберігаються у фронтендах як `/menu/classic.jpg`,
`/menu/signature.jpg`, `/menu/beef.jpg`; ці шляхи надходять у `imageUrl`.
Редактор каталогу підтримує http(s)-посилання та `/menu/назва.jpg`.

## Одноразове підтвердження кухнею

`POST /api/orders/:id/accept` з `{ "delayMinutes": 0 }` встановлює
`confirmedReadyAt = baselineReadyAt + delayMinutes`, фіксує `acceptedAt`
та повідомлення. Допустимі зсуви: 0, 5, 10, 15 хвилин.

Замовлення залишається `new` у черзі. Повторення того самого підтвердження
ідемпотентне; спроба змінити зсув після підтвердження повертає 409.

## Приготування та видача

`PATCH /api/orders/:id/status` з `{ "status": "cooking" }`.
Дозволені переходи: `new -> cooking -> ready -> archived`.
Кухня може повернути `cooking -> new`, `ready -> cooking` та
`archived -> ready`. Підтверджений час при цьому зберігається.
Перед приготуванням потрібне підтвердження кухнею.

Для scheduled перехід у `cooking` або `ready` раніше ніж за 20 хвилин
до **підтвердженої** видачі повертає HTTP 409:

```json
{
  "code": "EARLY_START",
  "error": "Це замовлення на майбутнє. Підтвердьте раннє приготування",
  "readyAt": 1792661400000
}
```

Після явного підтвердження кухарем повторити запит з `confirmEarly: true`.
Рядок `"true"` не приймається. Рівно за 20 хвилин підтвердження не потрібне.
Прямий перехід із `new` у `ready` заборонений.

## Знімки та події

`GET /api/orders` повертає `{ orders, archivedOrders, availability }`.
`GET /api/events` — SSE без буферизації. Події:

| Подія | Дані |
| --- | --- |
| `init` | Повний знімок замовлень і availability |
| `new_order` | Повне замовлення |
| `order_status_updated` | `{ id, status, order }`, зокрема після підтвердження часу |
| `availability_updated` | Об'єкт availability після стопу/відновлення |
| `reset` | `{ orders: [], archivedOrders: [] }` після очищення замовлень |

При перепідключенні клієнти відновлюють увесь стан через `init` і резервний
polling раз на 3 секунди. Історія подій не відтворюється.

Додатково: `GET /api/health`, `GET /api/analytics`, `POST /api/reset`.
`reset` очищає активні та архівні замовлення, зберігає порожній стан у SQLite
та не змінює послідовність номерів. Порожня база не генерує демо-замовлень.
Авторизація реалізована для адміністративного стопу та `/api/admin`.


## Меню та одна активна точка

`GET /api/points` повертає тільки активну демо-точку. `GET /api/menu`:
`{ point, products, categories, modifiers, revision }`. Приховані позиції
не передаються клієнту; стоп-лист має `available: false`.

`availability` також містить `point`, `openMinute`, `closeMinute`, `closed`.
Сервер враховує день тижня та винятки дат. Подія SSE `menu_updated`
передає нове публічне меню; зміни графіка додатково надсилають `availability_updated`.

Клієнт передає `pointId: "demo"`, `expectedTotal`, `promoCode`, а в позиціях
`productId`, `qty`, `lavashId`, `addedModifierIds`, `removedModifierIds`,
`spicinessLevel`. Сервер сам рахує ціни; клієнтські unitPrice/totalPrice не
використовуються. Невідповідна очікувана сума або недоступний товар — 409
до імітації оплати. Для сумісності підтримується пошук позиції за точною назвою.
Замовлення зберігає знімок складу, `unitPrice`, сум, `pointId`, `pointName`.

## Admin API

Усі запити мутації — `application/json`, з same-origin перевіркою Origin.
Токени не повертаються в JSON, сесія передається HttpOnly/SameSite=Strict cookie
`shawarma_admin` з Path=/api/admin. Тривалість — 8 годин; в HTTPS cookie Secure.

| Метод | Шлях | Призначення |
| --- | --- | --- |
| POST | `/api/admin/session` | `{ password: ADMIN_TOKEN }`, встановлення cookie |
| DELETE | `/api/admin/session` | Вихід, видалення сесії |
| GET | `/api/admin/state` | Точки, каталог, меню точок, модифікатори, останні 50 замовлень, журнал |
| POST | `/api/admin/points` | Нова неактивна точка, name/address обов'язкові |
| PATCH | `/api/admin/points/:id` | Налаштування, знижки, прийом, weeklyHours/exceptions |
| POST | `/api/admin/points/:id/products` | Нова позиція каталогу та підключення до меню точки |
| PATCH | `/api/admin/points/:id/menu/:productId` | Підключення товару / зміна price, visible, available, sortOrder, product |
| PUT | `/api/admin/modifiers` | Масиви add, remove, lavash, spiciness |

`id` і `active` не можна змінювати через налаштування точки; спроба — 409.
Публічні замовлення на будь-яку іншу точку відхиляються. У БД також є унікальний
індекс, що дозволяє лише одну активну точку.

`weeklyHours` — масив із 7 правил від понеділка до неділі, кожне
`{ closed: false, open: "10:30", close: "21:45" }`.
`exceptions` — масив `{ date: "2026-12-31", closed: true, open: "10:00", close: "22:00" }`.
Дата-виняток має пріоритет над звичайним днем. Прийом можна зупинити незалежно
від графіка через `acceptingOrders`.

Нові ціни, графік або стоп-лист не переписують уже оформлені замовлення.
Каталог спільний, але ціна й доступність належать меню конкретної точки.
