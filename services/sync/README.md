# Shawarma Sync

Независимый Node.js 24 HTTP/SSE-сервис со встроенным SQLite, без npm-зависимостей.
Код фронтендов не импортируется и статические файлы не раздаются.

```bash
npm ci
npm run dev      # .env.dev, watch
npm run start:dev
npm start        # .env.prod
npm run start:prod
npm run check
npm test
```

Настройки в `.env.dev` и `.env.prod` (шаблоны `.env.dev.example` / `.env.prod.example`): HOST, PORT, ADMIN_TOKEN, DATABASE_PATH и начальные
часы работы. По умолчанию `0.0.0.0:3002`, dev-база `data/shawarma.sqlite`, prod-база `data/shawarma.prod.sqlite`.
В Docker каталог `/app/data` принадлежит пользователю node и вынесен в том.

База инициализируется одной активной демо-точкой и каталогом. Изменения меню,
расписания, стопа и заказов сохраняются. Новые точки могут быть только
неактивными. Начальные env-часы не перезаписывают уже сохранённый распорядок.

Админ-панель работает через `/api/admin` с HttpOnly-сессиями; начальный ключ
задаёт ADMIN_TOKEN. При смене ключа прежние сессии сбрасываются при запуске.
`PATCH /api/settings` переключает кафе и обеденный перерыв без пароля в KDS.
Авторизация админ-панели сохраняется. Новая база не содержит демо-заказов;
`POST /api/reset` очищает активные и архивные заказы без регенерации истории.

GET `/api/health` — проверка доступности. Контракт описан в `API.md`.
Оплата при получении. Бот отправляет реальные сообщения при заданном TELEGRAM_BOT_TOKEN; кухонные маршруты пока не требуют авторизации.


## Telegram-уведомления о заказе

В приватном серверном `.env.prod` задайте `TELEGRAM_BOT_TOKEN` существующего `@shaurmisha_pl_bot` и пересоздайте Sync через скрипт деплоя. Токен нужен только Sync; webhook отдельного bot-сервиса менять не нужно. Не добавляйте токен в Git или переменные `VITE_*`.

Клиент отправляет подписанный `telegramInitData` и выбор `notificationsEnabled`. Sync проверяет HMAC и срок сессии (24 часа) перед сохранением Telegram ID. Переданный отдельно Telegram ID игнорируется. Заказ из браузера или ручной заказ кухни не получает Telegram-адресата.

События `placed`, `confirmed`, `cooking`, `ready` сохраняются вместе с заказом в одной транзакции SQLite в `telegram_outbox`. Worker отправляет сообщения последовательно для одного заказа, повторяет сетевые/временные ошибки с задержкой, учитывает Telegram `retry_after`. Ошибки 400/403 помечаются как постоянные. Очистка заказов отменяет ещё не отправленные сообщения. Уникальный ключ заказ/событие предотвращает повторную постановку при возврате статуса через API. Telegram sendMessage не имеет idempotency key: при обрыве ответа после фактической доставки или аварии между отправкой и записью результата редкий повтор сообщения возможен.

Клиент не читает заказы и не подключается к SSE кухни. После оформления кнопка «Відстежувати статус» открывает чат бота и закрывает Mini App; при отказе от разрешения можно повторно подключить сообщения через `POST /api/client/notifications` с проверенным `telegramInitData` владельца заказа. Без разрешения заказ всё равно создаётся, но уведомлений не будет. Заказы не сохраняются в localStorage, при новом открытии показывается меню.

## Admin і фотографії

Production `/admin/` і адміністративний API використовують Basic Auth із приватних ADMIN_BASIC_USER / ADMIN_BASIC_PASSWORD; Caddy отримує згенерований скриптом bcrypt-хеш. Окремий Admin-контейнер роздає лише статичний React frontend. SQLite редагує виключно Sync.

Інгредієнти зберігаються у state.ingredients, позиції посилаються на їхні ID. Фото необов’язкове, без нього frontend показує іконку. Завантажені JPEG/PNG/WebP перевіряються Sharp, зменшуються до 1600px і зберігаються WebP в MEDIA_PATH або data/media біля БД. Цей каталог має бути на постійному диску; у backup потрібно включати не лише SQLite, а й фотографії.
